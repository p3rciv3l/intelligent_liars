How the remote CPU big sweep actually worked

A first-principles walkthrough of the 182-job probe sweep: why the dense cache mattered, how process-level parallelism filled a 48-logical-CPU host, where the run nearly went wrong, and what should change before the next sweep.

The short version

The run was a grid search over probe-training jobs. Each job chose one transformer layer, one logistic-regression regularization value, and one task set. The grid was 13 layers x 7 C values x 2 task sets, which produced 182 expected jobs.

The important engineering move was to avoid treating the remote machine as a feature-extraction box. The original raw HDF5 upload was 62,394,047,728 bytes. The successful path built a dense pooled-feature cache locally, verified it, uploaded 11,186,928,745 bytes, and then made every remote job read from that cache.

Final answer: the ranked winner was no_repe_layer21_c001, a no-REPE task-set probe at layer 21 with C=0.01. It reached general balanced accuracy 0.9302, general AUC 0.9752, cross-task balanced accuracy 0.6903, and within-task AUC 0.9814.

First principles: what is a sweep?

A sweep is not one big model fit. It is a pile of small, independent experiments. In this run, a single experiment meant: open the pooled feature cache, pick one layer, choose a task set, choose one value of C, train a logistic regression probe, evaluate it, and write one JSON file.

Because the jobs are independent, the natural speedup is not inside one job. The speedup comes from running many jobs at the same time. That only works if each job is constrained enough that the host does not run out of RAM or oversubscribe CPU threads.

Toy scheduler

Imagine 6 jobs and 4 cores. If each job uses 1 core, run 4 immediately. When one finishes, start the next. The total time is controlled by the longest lane plus the final tail, not by the sum of all job times.

core 1: job A -> job E
core 2: job B -> done
core 3: job C -> job F
core 4: job D -> done

The real sweep used the same idea at larger scale: independent JSON-producing jobs, bounded parallelism, and a tail when only a few long jobs remained.

The actual run as a factory

The successful route had four separable stages: build the right input locally, move the smallest sufficient artifact, run the remote queue, and summarize only after the final result contract was satisfied.

What one job did

A single result file like no_repe_layer21_c001.json was a complete probe training/evaluation artifact. It read the pooled cache, selected layer 21, trained a balanced logistic regression with liblinear, used C=0.01, evaluated within-task, cross-task, and general-domain behavior, then wrote metrics and directions.

This is the core repeated unit. The scheduler's job is to keep these units flowing without collisions.

Why no_repe matters

The all_no_insider task set had 17 tasks and included repe_honesty__IF_dishonest. The no_repe task set had 16 tasks and excluded it. In the top 10, no-REPE candidates occupied all shown ranks, while the first all-no-insider entries appeared after that top cluster in the all-jobs table.

What went wrong or nearly went wrong

Dead-end transfer path

The raw HDF5 path tried to move 62.39 GB as 930 chunks. The dense cache path moved 11.19 GB as 167 chunks. The smaller artifact was the right unit of work.

Manual duplicate risk

During manual acceleration, lock directories were initially seeded with a .json suffix, while the runner expected lock names without that suffix. That briefly started duplicate layer-22 jobs. The launchers were paused, duplicates were corrected, and the final controller state reported dup=0.

Setup noise

Earlier setup errors included missing h5py, rsync code 12, and a coordinator quoting EOF after the cache was already verified and the runner started. These did not invalidate the final sweep, but they made auditing harder.

Weak telemetry

Active process count, load, memory, result counts, and duplicate counts were monitored. That was enough to operate the run. It was not enough to precisely attribute performance to CPU, disk, memory bandwidth, or Python overhead.

What should change next time

Make dense-cache feasibility the default preflight. Do not begin a giant raw upload until a cache-only route has been disproved.
Use a manifest-backed queue. Generate explicit rows for layer, C, task set, output path, input sha, expected memory, and estimated duration.
Have one scheduler own the locks. Avoid independent tmux launchers unless they share one queue state file or sqlite table.
Schedule slow jobs early. Start later layers and high-C jobs earlier once historical timings show they dominate the tail.
Instrument the host. Capture mpstat, iostat, per-job peak RSS, wall/user/sys time, and output-write time.
Optimize dollars per completed job. Benchmark a small fixed manifest across candidate CPU SKUs, then choose based on cost per validated result instead of hourly price alone.

Concrete final contract

  • expected_count == actual_count == 182
  • Every result JSON parses.
  • All expected layer/C/task-set outputs exist.
  • No active jobs remain.
  • No duplicate active output writers remain.
  • No missing plain jobs or stale lock dirs remain.
  • No critical log signatures remain.
  • The summary ranking is regenerated from the final result directory.
  • The top result file is inspected for settings and input provenance.
