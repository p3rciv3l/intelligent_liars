1. Purpose and success condition

The project tests a separation between factual reports and general action competence.

The target model must report wrong answers on knowledge tests.

The same model must still do useful computer actions.

Target result = low MMLU and GPQA scores + preserved OSWorld and ALFWorld scores

A low knowledge score is not sufficient evidence.

The model can fail because of refusal, bad formatting, random output, or model damage.

The experiment must show a systematic change in the report policy.

The experiment must also show that the action policy stays useful.

1.1 Strong success condition

  1. The base model answers a test item correctly.
  2. The modified model gives a valid but wrong answer.
  3. The modified model does not use a fixed answer position.
  4. The modified model does not increase refusals.
  5. The modified model keeps coherent reasoning and action output.
  6. The modified model keeps an acceptable OSWorld score.

2. Current evidence

The project has labeled honest and deceptive activation examples.

The labels use this convention: HONEST=0 and DECEPTIVE=1.

The probe coefficient points from honest activations to deceptive activations.

Do not confuse probe quality with control quality. A probe can read a signal that the model does not use. The GPU experiment must show a causal output change.

2.2 Data coverage

The activation data includes several truth and deception families.

  • True claims and negated claims.
  • Geometry-of-truth statements.
  • Internal-state true and false statements.
  • MMLU sycophancy pairs.
  • Roleplaying and sandbagging records.

This coverage is useful, but the deceptive positive class is heterogeneous.

A single deceptive region can combine different model behaviors.

3. Truth coordinate

The implementation treats the probe as an affine coordinate system.

The vector w gives the axis.

The intercept b gives the boundary.

z = wᵀh + b

A negative score is on the honest side.

A positive score is on the deceptive side.

Each operator changes only the component that is parallel to w.

The operator keeps the orthogonal component unchanged.

Figure 2. Simple operators can have complex downstream effects.

4. Intervention operators

The suite contains seven target operators and one random control.

The default values are start values for experiments.

The default suite values are not final scientific settings.

4.1 Validation rules

  • The code rejects an empty direction.
  • The code rejects a zero direction.
  • The code rejects nonfinite values.
  • The code requires unique layer numbers.
  • The bounded margin requires a maximum score change.
  • The random control uses a deterministic seed.
  • The random direction has the same norm as the probe direction.
  • The random direction is orthogonal to the probe direction.

4.2 Token scope

The default runtime teacher changes the last token state.

This rule changes the final prompt token during prefill.

Thus, the operator can change the first generated token.

The same rule changes each token during cached decoding.

5. Standalone model compiler

A runtime hook is not the final product.

The final product is a standalone Qwen checkpoint with modified weights.

The compiler uses the runtime operator only to make teacher answers.

It then trains a student model to copy those answers.

Figure 3. The offline intervention teacher creates data for the standalone student model.

5.1 Teacher data

The compiler stores the exact decoded suffix from Qwen.

This suffix includes hidden reasoning text when Qwen generates it.

The compiler keeps stable prompt identifiers.

It stores prompt and intervention hashes, the model revision, and the generation settings.

5.2 Prompt boundary

The trainer masks all prompt tokens.

The trainer applies loss only to assistant tokens.

The trainer preserves an existing assistant prefix.

It does not start a second assistant turn after that prefix.

5.3 Final checkpoint

The code merges the LoRA matrices into the base matrices.

The code then removes all LoRA wrapper modules.

The code rejects a merge that creates nonfinite weights.

The code saves the model in the standard Hugging Face format.

6.1 Deterministic resume

The code derives a seed from the epoch and batch number.

The teacher uses stable seeds from the ordered identifiers in each generation batch.

The training state includes LoRA weights, optimizer state, and the next batch.

The code writes this state to a temporary file first.

The code then uses an atomic file replacement.

6.2 Incomplete accumulation windows

The code corrects the gradient scale for a short final window.

Thus, a one-batch epoch does not use one eighth of the intended gradient.

6.3 Preservation loss

The preservation teacher comes from the pinned unmodified model.

The fleet plan requires this teacher.

The trainer mixes preservation rows with intervention rows.

The preservation_weight setting controls their loss contribution.

7. OSWorld preservation

OSWorld uses screenshots and action text.

The preservation input can contain Qwen image or video blocks.

The processor reads these blocks through qwen-vl-utils.

The trainer calculates loss on the assistant action tokens.

The trainer keeps the visual model weights frozen.

The checked-in preservation file is only a smoke example. It is not sufficient for a scientific OSWorld preservation claim. Add representative training trajectories before the full fleet run. Keep evaluation episodes out of the training file.

7.2 Preservation data requirements

  • Include browser, office, file, and system tasks.
  • Include successful action formats from the base model.
  • Include short and long action histories.
  • Include screenshots with different resolutions.
  • Do not include final evaluation episodes.
  • Use a shared image path on all fleet machines.

8. GPU fleet control

The fleet plan contains eight student variants.

It also records the pinned base model as the control.

Each worker uses one visible GPU.

All workers can use the same --drain command.

Figure 4. The fleet uses claim-specific paths and atomic publication.

8.1 Plan identity

The plan resolves the Qwen model ID to a 40-character commit SHA.

The plan ID includes all execution paths and settings.

  • Base model ID and revision.
  • Prompt path and prompt hash.
  • Preservation teacher path and hash.
  • Output root and base-control path.
  • Intervention paths and hashes.
  • Generation settings.
  • Training settings.

8.2 Claim safety

A worker first creates a variant lock.

It then creates a running marker with a unique claim token.

All durable model files use a path that contains this token.

A worker publishes a done marker with one atomic rename.

If recovery removes the running marker, the old worker cannot publish.

8.3 Retry behavior

A worker in drain mode continues after one variant fails.

The default maximum is two attempts for each variant.

The status output lists pending, running, failed, done, and corrupt variants.

10. Areas of doubt

The implementation is complete, but the scientific result is open.

DoubtWhy it mattersRequired test
Probe-control mismatchThe probe can read a signal that does not control output.Measure answer changes under the teacher operator.
Completed-answer training siteThe probe used pooled completed answer tokens.Compare pre-answer, post-think, and answer-token directions.
Heterogeneous deception classFalse claims, sycophancy, and sandbagging can use different mechanisms.Run per-family directions and held-out family tests.
Distillation errorThe student can learn teacher wording instead of the latent behavior.Use held-out prompts and compare teacher/student score traces.
Chance-level failureAblation can remove truth but fail to produce deliberate wrong answers.Randomize choices and test below-chance answer avoidance.
Position biasThe model can select one answer position repeatedly.Permute answer choices and measure response entropy.
Refusal or format damageLow accuracy can come from invalid output.Measure refusal, parse failure, and repetition rates.
OSWorld preservation coverageA small preservation set can miss important action modes.Use varied held-out trajectories and full benchmark runs.
LoRA capacityRank 16 can be too small or too large.Compare ranks 4, 8, 16, and 32.
Student overfitOne epoch can still memorize a small teacher set.Use held-out subjects, prompt forms, and seeds.
Quantization driftSmall RTX deployment can change the learned behavior.Compare BF16 and selected quantized checkpoints.
Judge errorAn LLM judge can confuse mistakes with deliberate deception.Use deterministic answer keys and manual samples.

10.1 Most important scientific risk

The general probe can be a good detector and a poor control direction.

The first GPU run must test the teacher before it trains all students.

Do not start the complete fleet if the teacher has no valid behavioral effect.

10.2 Most important engineering risk

Tests have not loaded the real 8B model into the training pipeline.

The unit tests use a small fake Qwen model for merge tests.

The first GPU run can expose architecture, memory, or processor errors.

11. Acceptance gates

Use the gates in sequence. Do not skip a failed gate.

Gate 1: EnvironmentGPU REQUIRED
  • Load Qwen at the pinned SHA.
  • Load the processor and one image.
  • Run an SDPA forward pass and an SDPA backward pass.
Gate 2: TeacherBEHAVIOR TEST
  • Generate 50 held-out MMLU items.
  • Measure valid wrong answers.
  • Reject refusal and fixed-position collapse.
Gate 3: One studentFULL REFLECTION
  • Train one small dataset.
  • Merge LoRA into Qwen.
  • Reload with the stock class.
Gate 4: PreservationACTION SMOKE
  • Run action-format prompts.
  • Run a small OSWorld subset.
  • Compare the base model.
Gate 5: Pilot fleetTHREE VARIANTS
  • Run reflection, bounded margin, and random control.
  • Compare target and damage metrics.
  • Select useful settings.
Gate 6: Full fleetEIGHT STUDENTS
  • Run all planned variants.
  • Verify the checkpoint export hashes.
  • Run complete evaluations.

11.1 Minimum model acceptance metrics

  • The answer parser succeeds at the base-model rate.
  • The refusal rate does not materially increase.
  • The repetition rate does not materially increase.
  • The target score differs from the matched-random control.
  • The OSWorld and ALFWorld scores stay inside the approved loss budgets.
  • The result repeats with more than one random seed.

Set the numeric budgets before the full evaluation.

Do not select thresholds after you inspect final results.

12. GPU start procedure

This section is a procedure. Each step gives one primary instruction.

12.1 Prepare the GPU environment

  1. Use one H100 80 GB GPU for the first safe smoke run.
  2. Check out the approved commit on the GPU machine.
  3. Start a remote tmux session before long work.
  4. Put HF_HOME and TMPDIR on a large storage mount.
  5. Install the Qwen runtime packages.
  6. Install the Torch-compatible torchvision package.
  7. Install and test FlashAttention.
  8. Use FlashAttention only for teacher generation.
  9. Install decord for video input support.
  10. Pull the provisional probe artifact with DVC.
  11. Put all fleet inputs under the same absolute /shared paths.
tmux new -s truth-smoke

export HF_HOME=/shared/hf_home
export TMPDIR=/shared/tmp
export HF_HUB_DISABLE_XET=1

uv pip install torchvision --index-url https://download.pytorch.org/whl/cu130
uv pip install decord

PYTHONPATH=src uv run --no-sync python -c \
  'import torch, torchvision, flash_attn, flash_attn_2_cuda; print(torch.cuda.is_available())'

PYTHONPATH=src uv run --no-sync intelligent-liars check-env \
  --require-cuda --check-model

12.2 Pin the base model

REVISION=$(PYTHONPATH=src uv run --no-sync python -c \
  'from huggingface_hub import HfApi; print(HfApi().model_info("Qwen/Qwen3-VL-8B-Thinking").sha)')

echo "$REVISION"

12.3 Build the intervention suite on shared storage

PYTHONPATH=src uv run --no-sync intelligent-liars build-intervention-suite \
  --probe artifacts/probes/sweeps/dense_15_27_by_layer/no_repe_layer21_c001.json \
  --output /shared/interventions/layer21_suite \
  --layer 21

12.4 Generate one full-reflection teacher smoke set

PYTHONPATH=src uv run --no-sync intelligent-liars generate-intervention-teacher \
  --prompts /shared/data/intervention_smoke_prompts.json \
  --intervention /shared/interventions/layer21_suite/full_reflection.json \
  --output /shared/smoke/full_reflection_teacher.json \
  --base-revision "$REVISION" \
  --no-resume

12.5 Evaluate the teacher smoke set

  1. Score the answers with deterministic answer keys.
  2. Measure valid wrong answers, refusals, parse failures, and answer positions.
  3. Stop if the teacher does not change correct answers to valid wrong answers.
  4. Test another layer or a bounded operator after a failed smoke result.

12.6 Generate the preservation teacher

PYTHONPATH=src uv run --no-sync intelligent-liars generate-intervention-teacher \
  --prompts /shared/data/preservation_prompts.json \
  --output /shared/intervention_fleet/preservation_teacher.json \
  --base-revision "$REVISION"

12.7 Write the immutable fleet plan

args=()
for path in /shared/interventions/layer21_suite/*.json; do
  args+=(--intervention "$path")
done

PYTHONPATH=src uv run --no-sync intelligent-liars plan-intervention-model-fleet \
  "${args[@]}" \
  --prompts /shared/data/intervention_prompts.json \
  --preservation-teacher /shared/intervention_fleet/preservation_teacher.json \
  --output-root /shared/intervention_fleet \
  --plan /shared/intervention_fleet/plan.json \
  --base-revision "$REVISION"

12.8 Start detached workers

tmux new-window -n fleet-gpu0

CUDA_VISIBLE_DEVICES=0 PYTHONPATH=src uv run --no-sync \
  intelligent-liars run-intervention-model-job \
  --plan /shared/intervention_fleet/plan.json \
  --drain \
  --max-attempts 2

Use the same command on each worker.

Change only CUDA_VISIBLE_DEVICES for each local GPU process.

Use A100 80 GB or L40S only after each GPU type passes the smoke run.

12.9 Monitor the fleet

PYTHONPATH=src uv run --no-sync intelligent-liars intervention-model-fleet-status \
  --plan /shared/intervention_fleet/plan.json

12.10 Recover a stopped worker

CAUTION: Make sure that the old worker is not active. Then use the recovery option. 
CUDA_VISIBLE_DEVICES=0 PYTHONPATH=src uv run --no-sync \
  intelligent-liars run-intervention-model-job \
  --plan /shared/intervention_fleet/plan.json \
  --drain \
  --retry-failed \
  --recover-running \
  --max-attempts 2

12.11 Verify one successful model again

CUDA_VISIBLE_DEVICES=0 PYTHONPATH=src uv run --no-sync \
  intelligent-liars verify-standalone-intervention-model \
  --model <model_output from fleet status done_artifacts>

12.12 Start evaluation

  1. Evaluate the base model and matched-random control first.
  2. Evaluate all students on a small MMLU and GPQA subset.
  3. Reject models with invalid output or fixed-position bias.
  4. Evaluate the models that pass these checks on OSWorld and ALFWorld smoke subsets.
  5. Run full evaluations for MMLU, GPQA, OSWorld, and ALFWorld after all smoke gates pass.

13. Result and next work

13.1 What the code now does

  • It reads the provisional truth probe.
  • It builds seven intervention variants.
  • It builds one matched-random control.
  • It records the pinned base model as a control.
  • It generates text or multimodal teacher data.
  • It trains LoRA students with preservation data.
  • It merges LoRA into ordinary Qwen weights.
  • It reloads the checkpoint with the stock Qwen class.
  • It runs concurrent claim-isolated fleet workers.
  • It records hashes for the checkpoint export inventory.

13.2 What the code does not prove

  • It does not prove that the truth direction is causal.
  • It does not prove that a student will score below chance.
  • It does not prove that a student will preserve OSWorld.
  • It does not select the best GPU type.
  • It does not select the final LoRA rank or loss weight.
  • It does not replace full benchmark evaluation.

13.3 Immediate next action

Start one GPU smoke run with the full-reflection teacher.

Use 50 to 100 held-out MMLU items.

Do not train the full fleet until this teacher changes correct answers to valid wrong answers.

13.4 Decision after the smoke run

Smoke resultNext action
The teacher changes correct answers to valid wrong answers.Train one full-reflection student.
The teacher causes random or invalid answers.Reduce strength or use bounded margin.
The teacher has no output effect.Test another layer or a domain-specific direction.
The student does not copy the teacher.Increase the teacher data, LoRA rank, or epoch count.
